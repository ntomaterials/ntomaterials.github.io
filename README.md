# Тест «Какой профиль НТО тебе подходит?»

Статический сайт: школьник отвечает на вопросы по единой 4-балльной шкале и получает
топ-3 профиля Национальной технологической олимпиады с процентом совпадения,
объяснением «почему подходит» и предупреждениями, если результат неоднозначный.

Весь расчёт — детерминированная арифметика в браузере пользователя. Бэкенда,
базы данных и сетевых запросов во время прохождения теста нет; ответы никуда
не отправляются и нигде не сохраняются.

---

## Быстрый старт

```bash
npm install          # один раз
npm run dev          # локальный сервер с горячей перезагрузкой
npm test             # тесты расчёта и валидации данных
npm run build        # сборка сайта в ./dist
```

Готовый `dist/` — обычная статика: можно открыть на любом хостинге без настройки сервера.

| Команда                | Что делает                                                            |
| ---------------------- | --------------------------------------------------------------------- |
| `npm run dev`          | Dev-сервер Vite. Правка CSV сразу перезагружает страницу.              |
| `npm run build`        | Сайт в `dist/` (+ service worker для офлайна).                         |
| `npm run build:single` | Один самодостаточный файл `dist-single/index.html` для работы офлайн.  |
| `npm run preview`      | Локальный просмотр собранного `dist/`.                                 |
| `npm test`             | Vitest: расчёт на ручных примерах + валидация реальных и битых данных. |
| `npm run typecheck`    | Проверка типов без сборки.                                             |

Требуется Node.js 20 или новее.

## Формат данных

Все три файла читаются **только на этапе сборки** и попадают в бандл готовым JSON.
В рантайме `fetch` к CSV не происходит. Кодировка — UTF-8, разделитель — запятая,
поля с запятыми внутри — в двойных кавычках.

Ничего из размерностей в коде не зашито: число профилей, кластеров, типов
деятельности и вопросов определяется из самих файлов.

### `data/nto_matrix_with_activities.csv` — матрица весов

Первые две колонки — служебные, дальше по одной колонке на каждый профиль.

```csv
block,group,АБП,АТС,ИРС,…
A,ИТ-базовый,3,2,2,…
A,ИИ и данные,2,3,2,…
Б,Программирование,3,2,2,…
Б,Конструирование,0,3,2,…
```

| Колонка          | Значение                                                                      |
| ---------------- | ----------------------------------------------------------------------------- |
| `block`          | `А` (или `A`) — предметный кластер, `Б` (или `B`) — тип деятельности           |
| `group`          | Название кластера / типа деятельности. Уникально в пределах файла.             |
| остальные        | Вес связи, целое число 0–3. Заголовок колонки — код профиля.                    |

Смысл весов: `3` — кластер является ядром профиля, `2` — значимо связан,
`1` — сопутствующая связь, `0` — связи нет.

Разделение на блок А и блок Б идёт по колонке `block`. Порядок строк любой,
но он же определяет порядок компонент вектора.

### `data/nto_questions.csv` — банк вопросов

```csv
block,group,question_text,positive_3,positive_2,neutral_1,negative_0
А,ИТ-базовый,"Мне нравится разбираться…","Это моё главное увлечение…","Мне это интересно…","Слышал(а) об этом…","Скорее не интересно…"
```

| Колонка         | Значение                                                                    |
| --------------- | --------------------------------------------------------------------------- |
| `block`         | `А`/`A` или `Б`/`B` — должен совпадать с блоком строки матрицы               |
| `group`         | **Точное** название строки матрицы, к которой относится вопрос               |
| `question_text` | Формулировка вопроса                                                         |
| `positive_3`    | Вариант ответа с баллом **3**                                                |
| `positive_2`    | Вариант ответа с баллом **2**                                                |
| `neutral_1`     | Вариант ответа с баллом **1**                                                |
| `negative_0`    | Вариант ответа с баллом **0**                                                |

Шкала едина для всех вопросов (3 … 0), а формулировки вариантов — свои у каждого.
Ответы уже даны в той же шкале `[0 .. 3]`, что и веса матрицы, поэтому дополнительная
нормализация не нужна — балл компоненты считается прямым средним ответов.
Идентификаторы вопросов (`А-01`, `Б-03`) генерируются автоматически по порядку строк
внутри блока — в файле их держать не нужно.

Количество вопросов на одну строку матрицы произвольное: один, два или пять.
Балл компоненты — среднее по всем её вопросам.

### `data/nto_profiles.csv` — справочник профилей

```csv
code,full_name
АБП,Автоматизация бизнес-процессов
АТС,Автономные транспортные системы
```

`code` должен точно совпадать с заголовком соответствующей колонки матрицы,
`full_name` показывается в интерфейсе.

## Алгоритм расчёта

Реализована методика **взвешенного евклидова расстояния** (шаги 4–9 раздела 4 ТЗ).

1. **Вектор пользователя `U`**: ответы уже даны в шкале `[0 .. 3]` — той же, в которой
   живут веса матрицы, поэтому дополнительная нормализация не нужна. Значение
   компоненты — среднее ответов по вопросам этой строки.
2. **Вектор профиля `P[p]`** читается из матрицы напрямую — он уже в шкале `[0 .. 3]`.
3. **Веса компонент**: `w_i[p] = P_i[p] / Σ P_j[p]`. Компоненты с нулевым весом
   не влияют на результат — расхождение по теме, не связанной с профилем, не штрафуется.
4. **Расстояние**: `D(U, p) = √( Σ w_i[p] × (U_i − P_i[p])² )`, диапазон `[0 .. 3]`.
5. **Ранжирование** по возрастанию `D`, топ-3.
   Процент совпадения: `round((1 − D / 3) × 100)`.
6. **Проверки надёжности**: разрыв `D[2] − D[1] < 0.30` → предупреждение о близких
   результатах; совпадение лидера `< 45%` → предупреждение о невыраженных предпочтениях.
7. **Карточка профиля**: «почему подходит» — две компоненты с наименьшим взвешенным
   вкладом `w_i × (U_i − P_i)²` среди значимых для профиля; тип деятельности —
   строка блока Б с максимальным весом; предупреждение — темы, где вес профиля `≥ 2`,
   а балл участника `< 0.35`.

### Как заменить методику

Расчёт изолирован в `src/scoring/`. Шаги 5 и 6 — функции `componentWeights()`
и `weightedEuclideanDistance()` в [`src/scoring/euclidean.ts`](src/scoring/euclidean.ts);
они не знают ни про Dataset, ни про интерфейс.

Чтобы подключить другую формулу:

1. Реализуйте интерфейс `ScoringStrategy` из [`src/scoring/types.ts`](src/scoring/types.ts)
   в новом файле.
2. Добавьте её в массив `STRATEGIES` в [`src/scoring/index.ts`](src/scoring/index.ts).
3. Поменяйте там же `ACTIVE_STRATEGY_ID`.

Ни загрузчик данных, ни интерфейс при этом не меняются.

В комплекте уже есть вторая методика — средневзвешенный балл
`SCORE(p) = (4 × S_A + 2 × S_B) / 6` из первой части раздела 4 ТЗ
([`src/scoring/weighted-average.ts`](src/scoring/weighted-average.ts)).
Чтобы переключиться на неё, поставьте `ACTIVE_STRATEGY_ID = 'weighted-average'`.

Пороговые значения (0.30, 45%, 0.35, веса осей 4/6 и 2/6) собраны
в [`src/scoring/constants.ts`](src/scoring/constants.ts).

## Валидация данных при сборке

Сборка **падает с понятной ошибкой**, а не показывает сломанный тест. Проверяется:

- CSV читается, не пуст, содержит нужные колонки;
- в матрице есть строки обоих блоков; названия строк уникальны;
- веса — целые числа 0–3, ни одной пустой ячейки, длина строки равна числу профилей;
- у профиля есть хотя бы один ненулевой вес;
- коды профилей в матрице и в справочнике совпадают **в обе стороны**, без дублей и пустых;
- у каждого профиля заполнено `full_name`;
- `group` каждого вопроса находит строку матрицы и совпадает с ней по блоку;
- у каждого вопроса заполнены текст и все четыре варианта ответа;
- для каждой строки матрицы есть хотя бы один вопрос.

Ошибки собираются все сразу — за один прогон видно полный список. Пример вывода:

```
❌  Проверка данных теста НТО не пройдена

Данные теста не прошли валидацию (3 шт.). Сборка остановлена.

  • data/nto_matrix_with_activities.csv:3 — вес «5» в строке «C2», профиль «P3» —
    допустимы только целые числа от 0 до 3
  • data/nto_profiles.csv:4 — профиль «P9» есть в справочнике, но в матрице
    nto_matrix_with_activities.csv нет столбца с таким кодом
  • data/nto_questions.csv:3 — значение group «Опечатка в названии» не найдено среди
    строк матрицы nto_matrix_with_activities.csv. Допустимые названия блока
    А (предметные кластеры): «C1», «C2»
```

Проверить данные локально, не собирая сайт: `npm test`.

## Обновление контента без разработчика

Инструкция для методиста. Git устанавливать не нужно — всё делается в браузере.

### 1. Открыть нужный файл

1. Зайдите в репозиторий на GitHub.
2. Откройте папку **`data`**.
3. Нажмите на файл, который нужно поменять:
   - `nto_questions.csv` — формулировки вопросов и вариантов ответа;
   - `nto_matrix_with_activities.csv` — веса связей кластеров с профилями;
   - `nto_profiles.csv` — названия профилей.

### 2. Загрузить новую версию

**Способ А — правка прямо на сайте** (удобно для одной-двух формулировок):

1. Нажмите значок карандаша **✏️ Edit this file** в правом верхнем углу.
2. Внесите правки. Если в тексте есть запятая — весь текст возьмите в двойные кавычки:
   `"Мне нравится разбираться, как всё устроено"`.
3. Нажмите **Commit changes…**, в поле описания коротко напишите, что поменяли,
   и подтвердите кнопкой **Commit changes**.

**Способ Б — замена файла целиком** (удобно после правок в Excel):

1. Сохраните файл из Excel как **CSV UTF-8 (разделитель — запятая)**
   и **с тем же именем**, что в репозитории.
2. В репозитории откройте папку `data` и нажмите **Add file → Upload files**.
3. Перетащите файл — GitHub сам поймёт, что это новая версия существующего.
4. Внизу нажмите **Commit changes**.

### 3. Проверить, что сайт обновился

1. Откройте вкладку **Actions** в репозитории.
2. Сверху будет запуск с названием вашего коммита.
   - 🟡 жёлтый кружок — сборка идёт, обычно 1–2 минуты;
   - ✅ зелёная галочка — сайт уже обновлён;
   - ❌ красный крестик — в данных ошибка, сайт остался на прежней версии.
3. Обновите страницу теста через **Ctrl+F5** (на macOS — **Cmd+Shift+R**).

Пока сборка не прошла успешно, на сайте остаётся предыдущая рабочая версия —
сломанные данные до посетителей не доходят.

### 4. Что делать, если сборка упала

1. Вкладка **Actions** → нажмите на запуск с красным крестиком.
2. Слева выберите задачу **Сборка**, затем шаг **Проверить данные и расчёт**
   (или **Собрать сайт**).
3. Пролистайте лог до строк, начинающихся с `•` — там указан файл, номер строки
   и что именно не так. Например:

   ```
   • data/nto_questions.csv:14 — значение group «ИТ базовый» не найдено среди строк
     матрицы nto_matrix_with_activities.csv. Допустимые названия блока
     А (предметные кластеры): «ИТ-базовый», «ИИ и данные», …
   ```

4. Откройте указанный файл на указанной строке, исправьте и закоммитьте ещё раз.
   Сборка запустится автоматически.

Самые частые ошибки: название в колонке `group` не совпадает с названием строки
матрицы (лишний пробел, дефис вместо тире), пустая ячейка с вариантом ответа,
новый профиль добавлен в матрицу, но не в справочник.

## Деплой

Выбран **GitHub Pages** с автосборкой через GitHub Actions: репозиторий уже на GitHub,
отдельные аккаунты и токены не нужны, публикация полностью описана файлом
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml).

Настройка один раз:

1. Создайте репозиторий на GitHub и запушьте в него проект (ветка `main`).
2. В репозитории откройте **Settings → Pages**.
3. В блоке **Build and deployment** в поле **Source** выберите **GitHub Actions**.
4. Готово. Первый пуш запустит сборку; адрес сайта появится
   в **Settings → Pages** и в логе задачи **Публикация**.

Дальше любой пуш в `main` — включая замену CSV через веб-интерфейс — автоматически
пересобирает и публикует сайт. Ручных действий не требуется.

Локальный `package-lock.json` стоит закоммитить после первого `npm install`:
тогда CI ставит ровно те же версии зависимостей.

> Netlify и Vercel подключаются так же просто: команда сборки `npm run build`,
> каталог публикации `dist`. Workflow при этом не нужен.

## Встраивание через iframe

Тест не выставляет `X-Frame-Options` и не задаёт CSP — со своей стороны он
не мешает встраиванию. Ограничения могут прийти только от хостинга;
у GitHub Pages их нет.

```html
<iframe
  src="https://<аккаунт>.github.io/<репозиторий>/"
  title="Тест: какой профиль НТО тебе подходит"
  style="width: 100%; min-height: 640px; border: 0"
></iframe>
```

Чтобы убрать внутреннюю прокрутку, тест сообщает родительской странице свою высоту:

```js
window.addEventListener('message', (event) => {
  if (event.data?.type === 'nto-test:height') {
    document.querySelector('#nto-test').style.height = event.data.height + 'px';
  }
});
```

Рабочий пример лежит в [`public/embed.html`](public/embed.html) и после сборки
доступен по адресу `<адрес сайта>/embed.html`.

## Офлайн-режим

Реализованы оба варианта из раздела 10 ТЗ.

**Service worker.** При обычной сборке плагин
[`build/vite-plugin-service-worker.ts`](build/vite-plugin-service-worker.ts) генерирует
`sw.js` со списком файлов бандла. При первом заходе тест кэшируется целиком и дальше
открывается без интернета. Имя кэша выводится из хешей имён файлов, поэтому новая
сборка создаёт новый кэш, а старый удаляется при активации. Документ запрашивается
«сначала из сети» — обновления доезжают сразу, офлайн работает из кэша. Регистрация
включается только в собранном сайте по `http(s)`, в dev-режиме её нет.

**Один файл.** `npm run build:single` собирает `dist-single/index.html` со встроенными
JS, CSS и данными. Файл можно скачать, положить на флешку и открыть с диска —
интернет и веб-сервер не нужны. В CI он публикуется рядом с сайтом как
`nto-test-offline.html`.

Обе версии пересобираются автоматически при изменении CSV — отдельных действий не требуется.

## Технические решения

**Без фреймворка.** У теста три экрана и одно линейное состояние, разделяемого
состояния между компонентами нет. React или Vue добавили бы к бандлу больше,
чем весь остальной код, ничего не упростив. Интерфейс собирается вручную через
`document.createElement` (хелпер `h()` в [`src/ui/dom.ts`](src/ui/dom.ts));
`innerHTML` не используется нигде.

**PapaParse — build-time зависимость.** Он импортируется только из `build/`,
который исполняется в Node при сборке, и в клиентский бандл не попадает.

**Ответы живут только в памяти вкладки.** Ни `localStorage`, ни `sessionStorage`,
ни сетевых запросов: при перезагрузке страницы всё стирается.

**Доступность.** Варианты ответа — нативные `<input type="radio">` в `<fieldset>`:
работают стрелки, `Tab` и скринридеры без дополнительного кода. Дополнительно есть
горячие клавиши `1`–`4`. Автопереход к следующему вопросу срабатывает только после
выбора мышью или касанием — при переборе вариантов стрелками фокус остаётся на месте.
Тема следует системной настройке (светлая/тёмная), анимации отключаются при
`prefers-reduced-motion`.

## Решения по расхождениям в исходных данных

Зафиксировано, чтобы при следующем обновлении ТЗ было понятно, почему сделано так.

1. **В ТЗ описаны два разных алгоритма.** В начале раздела 4 — средневзвешенный балл
   `SCORE = (4 × S_A + 2 × S_B) / 6` с ранжированием по убыванию, дальше — взвешенное
   евклидово расстояние с ранжированием по возрастанию. Они дают разные топ-3.
   По согласованию основной сделана евклидова методика: она расписана по шагам 1–9,
   подтверждена сводной таблицей параметров, и именно её шаги 5–6 ТЗ просит вынести
   в отдельный модуль. Вторая методика реализована и переключается одной константой.

2. **Колонка `group` в блоке Б банка вопросов.** В присланном файле все пять вопросов
   блока Б имели `group = Универсальный`, чего нет в матрице. Значения заменены на
   названия типов деятельности (`Программирование`, `Конструирование`, `Исследование`,
   `Анализ данных`, `Проектирование`) — соответствие однозначно следует из текста
   вопросов и их порядка. Код при этом остался строгим: сопоставление идёт по точному
   совпадению названия, «умного» подбора по порядку нет, иначе перестановка строк
   методистом молча меняла бы результаты.

3. **Проверка «ровно 29 строк» заменена.** Раздел 9 требует падать, если в банке
   не ровно 29 вопросов, но разделы 3.2 и 4 требуют не зашивать количество в код.
   Реализована проверка по смыслу: у каждой строки матрицы должен быть хотя бы
   один вопрос, а число вопросов берётся из файла.

4. **Исходные CSV лежали в корне проекта**, файл вопросов — с лишним символом в имени
   (``nto_questions.csv`.csv``). Рабочие копии положены в `data/` под каноничными
   именами; содержимое, кроме пункта 2, не менялось. Исходники в корне проекта
   оставлены нетронутыми — их можно удалить, чтобы методист случайно не отредактировал
   файл, который сборка не читает.

5. **Банк вопросов переведён с 5-балльной шкалы на 4-балльную.** По уточнению формат
   изменён: колонки `positive_2/positive_1/neutral_0/negative_1/negative_2` (баллы
   +2…−2) заменены на `positive_3/positive_2/neutral_1/negative_0` (баллы 3…0).
   Формулировки перенесены один в один (новая `positive_3` = старая `positive_2`,
   новая `positive_2` = старая `positive_1`, и т.д.) — из шкалы убран только самый
   крайний отрицательный вариант (старая `negative_2`, например «Совсем не моё…»).
   `data/nto_questions.csv` пересобран по этому правилу. Поскольку ответы теперь
   уже лежат в шкале матрицы `[0 .. 3]`, шаг нормализации (`u_norm = 3×(answer+2)/4`)
   из кода убран — `buildUserVector()` в
   [`src/scoring/user-vector.ts`](src/scoring/user-vector.ts) считает вектор
   пользователя прямым средним по сырым баллам.

## Замечания по калибровке методики

Алгоритм реализован ровно так, как описан в ТЗ, без изменений логики. Пороги
надёжности (раздел 4, шаг 8) вынесены в [`src/scoring/constants.ts`](src/scoring/constants.ts)
и не менялись при переходе на 4-балльную шкалу; менять их без решения авторов методики
не следует. При прогоне на реальных данных после перехода со шкалы {−2…+2} на шкалу
{0…3} (см. пункт 5 выше) видно, что часть прежних замечаний по калибровке ушла сама
собой, а часть осталась.

**Стало лучше: чётко выраженные ответы больше не помечаются как «неоднозначные».**
На шкале {−2…+2} разрыв между 1-м и 2-м местом почти всегда оказывался меньше порога
`gap < 0.30`, даже при явном интересе к одной области. На шкале {0…3} два проверенных
сценария с ясно выраженным интересом (программист/анализ данных, биология/химия) дают
gap 0.38 и 0.35 — выше порога, предупреждения нет. Отчасти это следствие смещения
шкалы ответов от симметричной {−2…+2} к несимметричной {0…3}: у профиля с достаточно
плотным набором смежных направлений (например, все варианты робототехники — ВРС, БАС,
ИРС, ЛР) разрыв всё ещё может оказаться ниже 0.30 даже при чётком выборе — это
отражает реальное пересечение таких профилей в матрице весов, а не только порог.

**Стало лучше: максимально отрицательные ответы теперь корректно ловятся как низкая
вовлечённость.** Если участник выбирает вариант с минимальным баллом (`negative_0` =
0) на все вопросы, лидер получает 41% — ниже порога `< 45%`, предупреждение
показывается. На прежней симметричной шкале такого не происходило: минимальный ответ
(`−2`) после нормализации давал 0, но нейтральный вариант (`0`) — середину диапазона
(`1.5`), которая уже была близка к типичным весам профилей.

**Осталось: нейтральные ответы всё ещё дают довольно высокий процент.** Если
участник отвечает «нейтрально» (`neutral_1` = 1) на все вопросы, лидер получает около
72% — заметно ниже, чем 83% на прежней шкале, но всё ещё выше порога `45%`.

**Осталось: случайные ответы не ловятся проверкой вовлечённости.** Чередование
вариантов без всякой связи с содержанием вопроса (например, «через один») даёт
разрыв около 0.01 (срабатывает предупреждение о близких результатах), но лидер
всё равно набирает около 74% — выше порога `45%`. Если задача проверки — поймать
«прокликал не думая», сейчас это ловит только проверка на близость результатов,
а не на процент лидера; порог вовлечённости стоит либо снизить, либо дополнить
проверкой на разброс ответов.
